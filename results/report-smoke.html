1. What was tested

Every test run is one Service Bus message sent from a laptop to the topic llm-tests. The topic fans it out to three subscriptions, each consumed by its own Container App that scales from zero (KEDA azure-servicebus scaler with the managed identity). All three workers run the same container image; only WORKER_MODE differs. Results land in a Blob Storage account reachable from the apps only through its private endpoint.

2. Impact on the application code

Standard → Flex: one parameter

client.chat.completions.create(
    model=deployment,
    messages=[{"role": "user", "content": prompt}],
    service_tier="flex",   # was "default"
    reasoning_effort="low",
    max_completion_tokens=1000,
)
# + client timeout raised to 900 s
# + retry/backoff on HTTP 429 (no capacity)

The Standard and Flex workers share the same function (worker/app/llm.py, 128 lines incl. retry logic). Synchronous request/response is preserved; the application only needs to tolerate longer and more variable latency and occasional 429s, which asynchronous, queue-driven processing handles naturally.

Standard → Batch: different architecture

# 1. build JSONL, model = GlobalBatch deployment per line
# 2. upload file   files.create(purpose="batch")
# 3. wait until the file is "processed"
# 4. batches.create(input_file_id, endpoint,
#                   completion_window="24h")
# 5. persist job state (blob) – the worker may scale to 0
# 6. schedule a poll message (Service Bus, +60 s) …
# 7. … repeat until completed/failed/expired
# 8. download output + error files, match custom_id

Batch needs its own worker (worker/app/batch_worker.py, 170 lines), a separate GlobalBatch deployment, durable job state, a polling mechanism (extra queue batch-status + second KEDA rule) and result correlation. Results come back as a file, not as a response.

9. Conclusions

  • Flex median latency was 1.78 s vs 2.07 s on Standard (0.86×), p90 2.15 s vs 2.79 s, max 2.25 s vs 2.86 s. 6/6 Flex requests succeeded (0 HTTP 429 responses were retried).
  • Flex needs no architectural change: same deployment, same SDK call, one extra parameter. Code must use a long timeout and handle 429 with backoff – both belong in any robust client anyway. It is a good fit for asynchronous, queue-driven workloads where a response in seconds-to-minutes is acceptable.
  • Batch job turnaround had a median of 7.2 min (min 7.2 min, max 7.2 min) versus 6.05 s for the same prompts on Standard. Batch requires a different application design (files, job state, polling, separate GlobalBatch deployment) and is suited to large offline workloads where the 24h window is acceptable.
  • Scale to zero worked for all workers: median message pickup delay 0.02 s, max 38.76 s. For Flex and Batch this overhead is negligible compared with the model latency.
