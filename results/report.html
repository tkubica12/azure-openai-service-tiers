1. What was tested

Every test run is one Service Bus message sent to the topic llm-tests – either from a laptop (send_tests.py, campaign main: 5 prompts per run) or by the scheduled Container Apps Job probe-job (campaign probe: 1 prompt every 15 minutes, day and night). The topic fans it out to four subscriptions, each consumed by its own Container App that scales from zero (KEDA azure-servicebus scaler with the managed identity). All workers run the same container image; only WORKER_MODE differs. Results land in a Blob Storage account reachable from the apps only through its private endpoint.

2. Impact on the application code

Standard → Priority / Flex: one parameter

client.chat.completions.create(
    model=deployment,
    messages=[{"role": "user", "content": prompt}],
    service_tier="priority",   # or "flex"; was "default"
    reasoning_effort="low",
    max_completion_tokens=1000,
)
# Flex: + client timeout raised to 900 s
#       + retry/backoff on HTTP 429 (no capacity)
# Priority: check response.service_tier – may be "default"
#           (downgraded, billed as Standard)

The Standard, Priority and Flex workers share the same function (worker/app/llm.py, 128 lines incl. retry logic). Synchronous request/response is preserved. Priority needs nothing else (it is a latency premium on the same deployment and quota); Flex needs tolerance for longer and more variable latency and occasional 429s, which asynchronous, queue-driven processing handles naturally.

Standard → Batch: different architecture

# 1. build JSONL, model = GlobalBatch deployment per line
# 2. upload file   files.create(purpose="batch")
# 3. wait until the file is "processed"
# 4. batches.create(input_file_id, endpoint,
#                   completion_window="24h")
# 5. persist job state (blob) – the worker may scale to 0
# 6. schedule a poll message (Service Bus, +60 s) …
# 7. … repeat until completed/failed/expired
# 8. download output + error files, match custom_id

Batch needs its own worker (worker/app/batch_worker.py, 198 lines), a separate GlobalBatch deployment, durable job state, a polling mechanism (extra queue batch-status + second KEDA rule) and result correlation. Results come back as a file, not as a response.

From about 10:00 UTC on 2026-09-29 the Batch control plane in Sweden Central degraded: the Files upload returned 408/504 and later POST /batches answered with 504 Gateway Time-out after 60 s even though the batch was created server-side. The original worker retried the message, got the same timeout, and dead-lettered it, leaving untracked (orphaned) batch jobs. Standard, Priority and Flex on the same resource were not affected. The worker now looks up an existing batch by metadata.run_id before creating one and after a failed create. Because job creation is not idempotent, a Batch client needs this extra care that a synchronous Flex call does not.

8. Metering and billing

How the service tiers show up in metering and on the bill – verified from the price list, Azure Monitor metrics and direct API checks:

  • Priority = premium meters. Priority usage is charged on dedicated PP meters (5.6 sol ShortCo Inp PP Gl, … Cd Inp PP Gl, … Opt PP Gl): gpt-5.6-sol Priority $8 / $0.8 / $40 vs Standard $4 / $0.4 / $20 per 1M input / cached / output tokens (2.0×). Requests that are downgraded to Standard (the response then says service_tier="default") are billed at the Standard price. Priority uses the same deployment and the same TPM quota as Standard.
  • Flex = discounted meters. Flex usage is charged on its own Flex meters (separate meter IDs from Standard), so in Cost analysis it can be separated by grouping/filtering on Meter. Flex input and output tokens cost 50 % of the Standard price of the same model; the cached-input discount applies on top. The public price list already contains Flex meters for the GPT-5.4 / 5.5 family (54 mini Inp Flex Gl, 54 mini Opt Flex Gl, 54 mini cd Inp Flex Gl); e.g. gpt-5.4-mini: Standard $0.75 / $4.5, Flex $0.375 / $2.25, Global Batch $0.375 / $2.25 per 1M input / output tokens. The public retail price API does not list a gpt-5.6-sol Flex meter yet, but Cost Management already charges it on dedicated meters (56sol ShCo Inp Fl Gl 1M Tokens, 56sol ShCo Opt Fl Gl 1M Tokens) – see the table below; the Flex estimate below uses 50 % of the Standard meter.
  • Same deployment, same quota. Standard, Priority and Flex requests go to the same GlobalStandard deployment and share its TPM/RPM quota – there is no separate "Flex deployment" or "Priority deployment" (Priority can optionally be made the deployment default). Batch in contrast needs a separate GlobalBatch deployment with its own enqueued-token quota and has its own Batch meters.
  • Metrics dimension. Azure Monitor metrics of the Foundry resource (ModelRequests, AzureOpenAIRequests, ProcessedPromptTokens, GeneratedTokens, TokenTransaction, TimeToResponse…) carry the dimensions ServiceTierRequest and ServiceTierResponse, so the tiers on one deployment can be charted and alerted on separately – and a mismatch (requested ≠ served) exposes Priority downgrades. (InputTokens/OutputTokens/TotalTokens do not have this dimension.)
  • Rejected Flex requests are free. A 429 "no capacity" answer is not billed; there is no automatic fallback to Standard – the client decides whether to retry Flex or send the request as Standard.
  • Tier selection. Request body service_tier (auto / default / priority / flex) or HTTP header x-ms-service-tier (the header wins). The response reports the tier that actually processed the request.

10. Conclusions

  • Priority median latency was 1.96 s vs 2.08 s on Standard (median paired ratio 1.05× over 162 prompts), p90 9.00 s vs 11.59 s. Median generation speed 41 tok/s vs 38 tok/s. 162/162 responses were actually served as Priority. Priority costs 2× the Standard token price and needs no code change beyond service_tier="priority" (or a deployment-level default).
  • Flex median latency was 2.28 s vs 2.08 s on Standard (median paired ratio 1.14×), p90 12.25 s vs 11.59 s, max 86.69 s vs 85.37 s. 219/219 Flex requests succeeded (0 HTTP 429 responses were retried).
  • Neither Priority nor Flex needs an architectural change: same deployment, same quota, same SDK call, one extra parameter. For Flex the code must use a long timeout and handle 429 with backoff – both belong in any robust client anyway – so it fits asynchronous, queue-driven workloads where a response in seconds-to-minutes is acceptable. For Priority the code should read service_tier of the response to detect downgrades.
  • Batch (reference) job turnaround had a median of 7.8 min (min 6.1 min, max 27.3 min) versus 2.20 s for the same prompts on Standard. Batch requires a different application design (files, job state, polling, separate GlobalBatch deployment); for the same 50 % discount Flex keeps the synchronous API.
  • Billing: Priority is charged on dedicated PP meters (2× the Standard token price) and Flex on dedicated Flex meters (0.5×); the public retail price API does not list the gpt-5.6-sol Flex meter yet, but Cost Management already charges it. All tiers use the same deployment and quota, and Azure Monitor separates the traffic with the ServiceTierRequest/ServiceTierResponse dimensions. Rejected (429) Flex requests are not billed and downgraded Priority requests are billed as Standard. Batch has its own deployment, quota and Batch meters. Meters seen in Cost Management: Priority 5.6 sol ShortCo Inp PP Gl 1M Tokens, 5.6 sol ShortCo Opt PP Gl 1M Tokens; Flex 56sol ShCo Inp Fl Gl 1M Tokens, 56sol ShCo Opt Fl Gl 1M Tokens. Implied output price from the actual charges (cost ÷ quantity): Standard $20.0, Priority $40.0 (2.00×), Flex $10.0 (0.50×) per 1M tokens.
  • Scale to zero worked for all workers: median message pickup delay 28.39 s, max 5.0 min. For Flex and Batch this overhead is negligible compared with the model latency.
